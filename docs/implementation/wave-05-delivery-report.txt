C. Database migration summary

Adds customer_payments, payment_allocations, payment_reversals, customer_refunds,
billing_schedules, billing_schedule_versions and billing_schedule_runs.
Adds one composite unique index to existing invoices; no existing financial
columns, historical rows, documents or subscription receipts are rewritten.
Customer credit is a projection, not a separate mutable balance table.

Money columns use DECIMAL(24,3); accepted input respects the existing supported
currency scales. Allocations reference both receipt and invoice through the same
(id, firm, customer, currency) tuple. Database checks enforce positive receipt,
allocation and refund amounts, nonnegative reversal amounts and valid counters.
Reversal uniqueness permits only one compensating record per receipt.
Request-key uniqueness and stored payload hashes reject conflicting replays.
Schedule/period uniqueness and unique generated invoice linkage prevent duplicate
period invoices. Aggregate read indexes start with firm ownership where needed.

Backfill: none. Historical external settlements must be entered as explicit,
reconciled receipts; no opening financial balances were guessed.
Rollout: validate and apply to a disposable MySQL database first, regenerate the
Prisma client, then run the deferred checks before any production rollout.
No migration was applied in this session. MySQL CHECK enforcement/version and
DDL lock duration remain deployment validation items.
Rollback before financial use can revert application exposure while leaving the
additive schema in place. After financial use, preserve all records and use a
reviewed forward fix/compensation; do not drop ledger tables to roll back.

  Permission payments.manage; feature payments.manage -> payments.record.

POST /billing-schedules/:id/approve, /pause, /cancel
POST /billing-schedules/:id/runs/:runId/retry
  Permissions billing.recurring AND invoices.create; features billing.recurring
  and billing.invoices. Workers revalidate the approved actor and both features.

Tenant ownership chart:
Firm -> Company -> CustomerPayment -> Allocation/Reversal/Refund
Firm -> Company -> Invoice <- Allocation
Firm -> Company -> BillingSchedule -> Version -> PeriodRun -> Invoice draft
Firm -> OutboxEvent -> JobAttempt; durable payload IDs are checked against that firm.
Firm -> required audit records; existing audit reads remain firm scoped.
PlatformCharge -> PaymentEvent remains a separate existing subscription ledger.

RBAC and plan checks occur on HTTP actions and again in command transactions.
Reads use consistent transaction snapshots; writes use the existing firm lock.
New features are not silently enabled for legacy subscriptions or existing plans.
The platform owner must explicitly include them in approved plan versions.
Payment record/manage grants imply view; manage also implies record. Recurring
grants imply invoice view/create; the backend still checks both actions explicitly.
No new receipt/schedule quota policy was invented. Existing PDF/storage quotas
continue to apply when generated drafts use the normal document workflow.
