How files flow

  Browser: upload / generate PDF / preview / download
                    |
                    v
  Feature API: authentication + firm/record permissions + file validation
                    |
          +---------+-----------------+
          |                           |
          v                           v
  Database metadata            Shared storage service
  firm ID, relative path,              |
  version, size and hash        STORAGE_DRIVER at startup
                                  /              \
                             local                s3
                               |                   |
                       STORAGE_LOCAL_ROOT     private Qorwell bucket
                                               environment prefix

Protected files are read through their authorized API routes. Public display
assets keep the existing /storage/... application URLs; the backend proxies the
S3 bytes for the approved image directories. The bucket itself remains private.
Multipart uploads use a short-lived, bounded operating-system temporary spool;
that spool is removed after success/failure. Successful S3 uploads do not keep a
permanent local copy. Temporary processing is different from persistent storage.
Storage outages return a safe error; S3 mode never silently writes to disk.

The actual name comes from Firm.name, not the display label of a different
company record. Names are normalized to safe folder text, capped at 40 Unicode
characters and combined with the firm ID. Indian-language letters are supported.
Firms with the same name remain separate because their IDs differ. A name with
no usable letters or numbers uses <id>-firm. Filenames remain UUID-based.

The saved path is authoritative. If a firm is renamed, existing files retain
their original name snapshot and continue to open; later files use the new name.
Uploads persist the exact path selected before receiving the file, so a rename
during upload cannot redirect the metadata to a different file. Validation checks
the firm ID, file area, asset type and filename; folder names grant no permissions.
Historical numeric folders are still supported. Existing files were not renamed
or moved by this naming change, and no database schema migration is required.

Copying files and switching providers safely
scripts/storage-migrate.ts defaults to dry-run, is copy-only and never changes DB
paths or deletes a source. It verifies size and SHA256, skips identical targets
and refuses conflicting targets. It rejects symbolic links and skips dotfiles.
A private storage-migration-manifest.json records the inventory/results and is
ignored by the backend repository. Preserve an applied manifest before rerunning.

For local -> S3, configure the intended bucket/prefix/root first, pause writers
and workers during the final copy and switch, then run from the backend:
  npm run storage:migrate -- --dry-run
  npm run storage:migrate -- --apply
Verify the manifest, select STORAGE_DRIVER=s3 and restart the backend. Verify old
and new records before allowing writes. Keep the original source until recovery
and retention requirements have been agreed; do not delete it as part of copying.

For S3 -> local, use a NEW empty STORAGE_LOCAL_ROOT, pause writers/workers and run:
  npm run storage:migrate -- --to-local --dry-run
  npm run storage:migrate -- --to-local --apply
Verify the manifest, select STORAGE_DRIVER=local with that exact new root, restart
and verify records before allowing writes. Do not switch back to an old disk copy:
S3-only uploads would be missing and files deleted in S3 might reappear. The script
refuses a local destination containing stale or differing files. Database paths
remain the same in either mode. Synchronization is explicit, not automatic dual
writing or fallback. S3 version recovery requires a separate authorized operator;
the application role intentionally cannot purge historical versions.

Cost choices
S3 Standard is appropriate for the current small, actively read documents. Same-
region placement avoids cross-region storage traffic. There are no new NAT
Gateways, load balancers, KMS customer keys, CDN or Lambda resources for storage.
SSE-S3 avoids separate KMS key/request charges. Public image responses have cache
headers; protected documents remain private/no-store. PDFs stream where their API
supports it, and existing small bounded renderer/export buffers remain bounded.

Official Stockholm price-index snapshot published 9 November 2026:
  Standard first tier: USD 0.023 per GB-month
  PUT/COPY/POST/LIST: USD 0.005 per 1,000 requests
  GET/other: USD 0.0004 per 1,000 requests
Example 10 GB + 10,000 PUT-type + 100,000 GET-type requests is about USD 0.32/month,
excluding transfer, taxes, retained old versions and other AWS services. This is
an estimate, not a bill or a usage guarantee. Versioning consumes extra storage
for old bytes; deletion markers hide a current file without removing history.
No archive transitions were added: small-file transition fees/minimum durations
can outweigh savings and retrieval latency is undesirable for active ERP files.
Agree a retention policy before expiring old versions or deleting original files.

Template source-control safety
infrastructure/storage.json is a CloudFormation infrastructure definition, not a
credential file or runtime .env. It contains no AWS keys, tokens, passwords or
private user files. Bucket names and account IDs are parameters/AWS-generated
references; committing the current template does not grant access or execute AWS
changes. It is appropriate to version the template for infrastructure review and
reproducibility. Applying a stack update is a separate explicit cloud operation.
Keep real .env files, keys, private access records and migration manifests out of
source control. Do not place secrets into this template in future edits.
