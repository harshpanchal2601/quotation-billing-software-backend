C. Database migration summary

Adds leads, opportunities, sales_tasks, sales_activities, sales_orders,
sales_order_lines, fulfillments, fulfillment_lines, sales_order_invoice_lines,
sales_order_history, portal_identities, portal_invitations, portal_sessions,
portal_grants and document_acceptances.

Adds invoices.source_sales_order_id, compound ownership/reference indexes and an
indexed (firm, source order, status) reservation lookup. Quotation history gains
portal_actor_name and a nullable changed_by_id so a customer is never fabricated
as a firm User. Existing staff-authored history remains unchanged.

Composite foreign keys bind customer links to their firm, fulfillment lines to
both the order and its line, invoice reservations to their actual source order,
and portal invitation/session/grant/evidence to the same firm/company/identity.
Owner/assignee foreign keys also bind the selected user to the same firm.
Creator/audit actor IDs remain server-derived and may represent a platform admin.

Unique constraints cover exact quotation-to-order conversion, firm request keys,
order line numbers/history versions, event line uniqueness, contact identity,
opaque token hashes, one decision per quotation revision and decision request keys.
CHECK constraints validate positive quantities, nonnegative opportunity values,
probability/version/status bounds and exactly one document per portal grant.
Quantity storage is DECIMAL(18,3); opportunity/allocation arithmetic uses existing
Decimal and supported currency precision. No stock ledger is written.

Backfill: none. No historical financial amounts or business identities are guessed
or rewritten. No migration was executed and no Prisma client was generated.
Review/apply the additive SQL on disposable MySQL first; regenerate the client and
run the deferred checks before rollout. Verify MySQL CHECK support and DDL locking.

Rollback before use may disable feature grants and retain the additive schema.
After order/invoice reservations or portal decisions exist, preserve them and use
a reviewed forward fix. Do not drop evidence or restore a pre-Wave-06 generated
client that assumes all quotation history actors are internal/non-null.

D. API domain feature authorization and tenant mapping

All staff paths below are under /api/v1. Firm identity comes from existing
authenticated tenant context, never a body field. Commands recheck roles/features
inside the firm-locked transaction; reads remain scoped and recheck access.

GET/POST /leads; GET /leads/options; PATCH /leads/:id
GET /leads/:id/suggestions; POST /leads/:id/convert
GET/POST /opportunities; PATCH /opportunities/:id
GET/POST /tasks; PATCH /tasks/:id
GET/POST /customer-timeline
  Feature crm -> companies. Reads crm.view; writes crm.manage. Non-admin firm
  users see assigned/owned or created records unless granted crm.view-all.
  Conversion requires companies.view or companies.manage for explicit creation.
  Quote source links separately require quotations.view and the quotation feature.

GET /sales-orders; GET /sales-orders/:id?historyPage=N
POST /sales-orders/from-quotation; POST /sales-orders/:id/cancel
POST /fulfillments; POST /fulfillments/:id/cancel
  Feature sales.orders -> quotations -> companies. Reads sales-orders.view;
  conversion/cancellation sales-orders.manage; completion fulfillments.manage.
  Conversion also requires quotations.view. Firm order capability must be enabled.

POST /invoices/from-sales-order
  Existing billing.invoices + invoices.create, plus sales.orders and
  sales-orders.view. Invoice drafts reserve only active completed quantities.
POST /invoices/:id/cancel-order-draft
  Existing billing.invoices + invoices.void. Audited, non-posting DRAFT -> VOID
  releases quantities, even if order creation was subsequently disabled.
  Existing issuance rechecks order capacity; existing valid financial voids release
  quantities. Issued credit/debit notes do not invent delivery returns/replacements.

GET /portal-access?companyId=N&page=N&historyPage=N
GET /portal-access/contacts?companyId=N
POST /portal-access/invitations; POST /portal-access/grants
POST /portal-access/{identity,invitation,grant}/:id/revoke
POST /portal-access/identity/:id/restore
  Feature customer.portal -> companies; permission portal.manage and firm portal
  capability. Sharing independently checks the appropriate document view permission
  and its feature. Reset revokes every old session/invitation/grant before binding
  the current contact email; no duplicate contact/customer identity is created.

POST /customer-portal/exchange; POST /customer-portal/session
GET /customer-portal/documents; GET /customer-portal/documents/:grantId
POST /customer-portal/decisions; POST /customer-portal/logout
  Separate opaque portal session namespace. No firm-user RBAC or selected-firm
  identity is inferred from email. Each request rechecks firm/plan/preset, identity,
  contact/company state, session/invitation revocation and document scope/expiry.
  Document features are also rechecked. Mutations require trusted Origin and the
  session's CSRF proof. Exchange consumes the invitation once and rotates sessions.

Ownership chart:
Firm -> existing Company/Contact/Address and Item masters
Firm -> Lead -> optional existing/new Company -> Opportunity -> Task/Activity
Firm -> exact accepted Quotation -> SalesOrder -> independent Lines/History
SalesOrder -> Fulfillment -> Lines; SalesOrder -> Invoice quantity reservations
Firm/Company/Contact -> PortalIdentity -> Invitation -> Session
PortalIdentity -> explicit Grant -> immutable customer document snapshot
Grant + Session + exact Quotation -> DocumentAcceptance + quotation status history
Firm -> required audit records; customer endpoints expose no internal audit rows.

New plan features have legacy=false and are not silently enabled on subscriptions.
Optional sales presets live in the existing versioned FirmBusinessPolicy. SERVICE
defaults to direct invoicing/orders off; TRADING and MIXED permit order completion.
Explicit flags can override those preset defaults, but never bypass subscription
or role checks. Old policy JSON remains valid; actual new feature access still
requires the new opt-in subscription grants.

Policy choices were delegated by the user during implementation. The chosen
pipeline is NEW 10%, QUALIFIED 25%, PROPOSAL 50%, NEGOTIATION 75%, WON 100%, LOST 0%.
These are product defaults, not a claim that every industry uses identical stages.
Intermediate probabilities can be edited; terminal stage probabilities stay 100/0.
The stage vocabulary is intentionally bounded; generalized stage/rule builders
remain excluded until Wave 08.

Partial order invoices use active completed quantities. Source prices/taxes remain
snapshots. Allocating remaining components and source charges/rounding preserves
the accepted total across partial invoices and cancellations, without a second
tax engine. Incompatible/corrupt source totals or unsupported currency precision
are rejected rather than silently recalculated.

Portal decisions are operational customer approval/rejection with explicit consent.
No legal signature certification is claimed. Evidence is retained without an
automatic purge or an invented statutory retention period. Invitation TTL is
bounded to seven days (UI uses 24 hours), sessions to one hour, and document grants
to ninety days (UI uses fourteen days). Staff deliberately deliver invitation links;
this implementation does not send uncontrolled external invitation emails.

Excluded / NOT IMPLEMENTED by scope: inventory posting/purchasing, generalized
automation/stage builder, certified digital signatures and automatic legal evidence
deletion. Actual browser/provider/production acceptance is NOT IMPLEMENTED in this
session because execution is deferred; no passing end-to-end result is claimed.
